# Nginx 아키텍처

## 한 줄 정의

이벤트루프 + epoll 기반의 비동기 HTTP 서버. C10K 문제를 소수 워커로 해결.

## C10K 문제 (1999)

Apache의 스레드 per 접속 방식:
- 동시 접속 10,000명 = 스레드 10,000개
- 스레드 하나 ~2MB → 20GB RAM
- 대부분의 스레드는 I/O 기다리며 idle

## Nginx의 해결책 — 이벤트루프

```
┌─────────────────────────────────────────┐
│           Nginx 워커 프로세스             │
│   (CPU 코어 수만큼만 존재. 보통 4~8개)    │
│                                         │
│  이벤트 큐 → 워커 → I/O면 OS에 위임     │
│             ↓                           │
│         CPU 작업이면 직접 실행(블로킹)   │
│                                         │
│  OS 완료 → 완료 이벤트 큐 → 워커 마무리 │
└─────────────────────────────────────────┘
              ↕ epoll
┌─────────────────────────────────────────┐
│              OS 커널                     │
│   실제 I/O 처리 (파일, 네트워크, 소켓)   │
│   완료되면 epoll에 알림                  │
└─────────────────────────────────────────┘
```

## epoll이란

Linux 커널의 I/O 이벤트 감지 메커니즘.
"관심 있는 소켓들 등록해놓고, 변화 생기면 알려줘" 라고 OS에 맡기는 것.
워커 1개가 소켓 1만 개를 동시 감시 가능.

## I/O vs CPU 작업 구분

```
OS에 위임 가능 (I/O):          OS에 못 넘김 (CPU):
  파일 읽기/쓰기   ✅             문자열 파싱       ❌
  네트워크 소켓    ✅             암호화 계산       ❌
  DB 쿼리 소켓     ✅             이미지 처리       ❌
  DNS 조회         ✅             로그 포맷팅/집계  ❌
```

CPU 작업 만나면 워커가 직접 실행 → 그 동안 이벤트 큐 못 꺼냄 → 블로킹.

## Node.js와의 관계

Ryan Dahl이 "Nginx에서 영감받았다"고 직접 언급.
```
Node.js:  싱글 스레드 + libuv (이벤트루프)
Nginx:    소수 워커   + epoll  (이벤트루프)
```
설계 철학 동일. I/O 작업은 OS에 위임, CPU 작업은 직접.

## Nginx에 로그 수집을 시키면 안 되는 이유

```
요청 파싱    → CPU 작업 ❌ → 워커 블로킹
포맷 생성    → CPU 작업 ❌ → 워커 블로킹
집계/필터링  → CPU 작업 ❌ → 워커 블로킹
파일 쓰기    → I/O 작업 ✅ → OS 위임 가능
```

로그를 많이 쏠수록 CPU 작업 비율↑ → Nginx 워커 블로킹 → 1만 명 처리하던 Nginx가 정체.

## Nginx 본연의 역할

- ✅ 정적 파일 서빙 (I/O)
- ✅ Reverse Proxy (소켓 I/O)
- ✅ SSL 종료 (CPU 있지만 최적화됨)
- ✅ 로드밸런싱 (라우팅만)
- ✅ HTTP access log (자신이 경험한 것만 — IP, URL, 응답코드)
- ❌ 애플리케이션 로그 수집 (앱 비즈니스 로직의 산출물)
